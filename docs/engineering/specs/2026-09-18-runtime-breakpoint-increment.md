`exhausted_cycles`。其他两范围的封装服务也处于失败状态。检查时备份卷剩余约
80,317,095,936 字节（74.8 GiB）；旧代码对任何大小的快照要求
`4 * MAX_BYTES + 1 GiB`，其中 `MAX_BYTES=20 GiB`，即固定预留81 GiB。
固定最坏上限误拦截了可安全完成的小快照，且资源不足耗尽了8次封装重试预算。

## 备份封装修复

- 用实际ZIP大小、声明展开量、文件块开销及1 GiB余量计算峰值空间：
  `3 * archive_bytes + expanded_bytes + MAX_FILES * 8192 + 1 GiB`。
  三份ZIP尺度覆盖复制、密文、解密中间件；复用已发布密文的恢复同样走预检。
- 保留ZIP文件数、重复成员、总展开量、私有托管和文件身份检查。
  空间估计不等于归档验证；实际加密、逐文件摘要、完整隔离恢复、状态相等及发布条件保持。
- 空间不足首次保留失败，后续调用继续返回失败并重新检查空间，不不断追加相同资源失败。
  原来的空间失败记录全部保留，并不再占用实际封装/完整性失败的8次预算。
- 损坏归档、摘要不符、密码/恢复失败仍受原有预算约束。错误命名空间或不合托管要求的
  失败元数据不能取得资源豁免。没有删除历史、修改RPO或伪造当前恢复点。

这是容量预检修复，不是备份卷无限扩容或保留策略。外部并发磁盘消耗仍可能导致真实I/O失败；
失败不能发布成功。旧快照在新版发布后必须真实重新封装/恢复，才能更新恢复点时效。

## 逐日账务重放

`services/research/demo_account_recovery.py::reconcile_days` 复用原恢复算法和唯一Decimal账本，
输出独立的 `DEMO_REPORTED_ACCOUNT_DAYS_V1` 技术报告，最多覆盖7个UTC日期。

- 保留原始初始资金、累计手续费、资金费、现金流、容量消耗、原系统订单及人工成交归属。
- 每日输出期初/期末钱包、价格损益、手续费、资金费、外部现金流及成本后净变化；
  钱包变化必须等于成本后变化加外部现金流。无事件日沿用原余额。
- 标明首尾是否完整UTC日，不把部分窗口称为完整日收益。报告不提供绩效准入或风险预算重置。
- 两次完整REST观察、原生逐笔核对、合约一致、边界/资金一致等校验继续生效。
  跨午夜仍持仓但没有可信午夜估值时，拒绝生成日权益；检查点本身跨午夜也拒绝。
- 原 `reconcile` 仍是同日合同，受保护执行路径继续使用它。新离线结果不会进入OMS恢复、
  新周期登记或自动交易准入。这一增量尚未完成跨日执行续接。

离线入口只读取已冻结的完整输入包，没有网络、凭证、签发或下单选项；输出必须是新文件：

```bash
/home/kerstker/quantos-dev-output/dgx-engine-foundation-20260905/venv/bin/python \
  -m tools.demo_account_day_replay \
  --input /absolute/development/frozen-account-inputs.json \
  --output /absolute/development/new-day-report.json
```

输入包含原 `opening/closing/statements/windows/system_orders/adv_notional/participation_rate`，
最高32 MiB；不支持重复JSON键、非普通文件或读取中变化。报告绑定输入摘要，
成功是技术账务匹配，`UNRESOLVED`保留报告并返回2；既有输出不能覆盖。
示例路径是占位，不代表已采集到当前真实账户的跨日证据。
