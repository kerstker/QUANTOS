## 具体执行顺序

`demo_cancellation.proposal` 从受保护状态重新读取原预留、发送标记及最新原 ID 查询。
只选择同批次、同部署、同计价币种、场所编号相符且仍处于 NEW/PARTIALLY_FILLED 的
订单；查询超过五秒、未知、编号冲突、无发送标记或已终态均不能准备撤单。
提交和撤单使用不同签名用途，原下单批准不能用作撤单批准，反向同样拒绝。
撤单上下文绑定原批次、原预留、确切编号、查询快照、账户、部署、当前进程和注册表。

实际受保护入口依次执行：状态保管检查 → 最新固定提案 → 独立签名验证 → 一次性
批准落盘 → 每单发送标记落盘 → 再查配置/有效期/输入 → 一次 DELETE → 响应记录。
撤单日志保存在执行目录的独立 `cancellations.sqlite3`，没有现金或持仓职能。
失去响应、响应保存失败或进程中断后，批准与发送标记仍在；相同批准不会重发。
注册表在凭证加载后的最终检查仍须有效。所有实际签名私钥继续由外部签发方保管，
本批代码不生成签名、HUMAN 身份或新的人工 mandate。

响应仅表示该次接口所报订单状态。即使返回 CANCELED，仍需原编号查询和私有回执
共同恢复原 OMS；若撤单过程中成交，则保留对应成交数量。撤单入口不清除恢复
阻塞、不写 OMS 成交、不更新持仓，也不从响应计算现金或收益。

## 前端与只读发布

新增 `DEMO_CANCEL_STATUS_V1`、Console `cancellation_status` 及对应 TypeScript
合同。Studio 显示原订单数、已保留发送标记数、已保存响应数、结果未知数及逐单
精确编号/数量。未发送、没有响应和已取得响应分别展示；所有响应继续指向原查询
恢复，不能显示成现金闭合或交易成功。手机沿用逐字段布局，长编号不转成浮点数。

执行侧在批准、发送标记及响应落盘后分别保存显示快照；结果写入失败仍留下未知
快照。共用有界内容寻址的显示文件存储，旧 OMS 文件字节格式和校验规则保持。
发布者使用 `tools.demo_oms_status_publish --kind cancellation`，源为
`/var/lib/quantos-demo-executor/evidence/cancellations/views`，目标为研究状态下的
`data/cache/binance_demo_cancel_status`；它只有结构校验与只读复制，不是撤单入口。
错误的显示类型、损坏、重叠目录和倒退时间不能覆盖已有视图。
