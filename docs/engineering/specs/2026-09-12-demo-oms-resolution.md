`live/execution/demo_oms_reconciliation.py` 先把原批准批次的发送标记、原 ID 查询和
私有回执导入原日志/唯一 Decimal 账本，再生成按内容摘要保存的恢复计划。仅在
每个订单均有完整终态回执、最新原 ID 查询相符、时间顺序成立且原账本可回放时，
计划才为 READY_FOR_OMS_PROJECTION。缺查询、最后查询失败、不同数量、缺费用、
流缺口或时间不成立均保留 UNRESOLVED，不清除恢复状态。

受保护的内部入口 `demo_prepared_execution.reconcile_reserved` 在原状态保管检查
之后，额外要求订单事件库和私有流库位于执行进程固定目录并由该执行身份保管。
该入口自行计算计划，不接受请求提供的“已通过”计划；研究用户可写的私有导入
不能直接清除受保护执行状态。入口没有 HTTP、凭证、发送、撤单或重新批准操作。
实际安装、独立签发配置和执行身份的私有采集驻留仍待接入。

计划通过后，复用原 OmsAuthority：恢复既有 PENDING_NEW 命令身份，逐条写原订单
事件库，再幂等投影到原订单读模型，最后才把相应 recovery 记录由 FOUND 转为
RESOLVED。每条原回执身份稳定，已落事件但未完成投影的崩溃可重放；整个批次未
恢复完时仍保留阻塞。已跳闸、不同订单身份、变化的原查询日志或不一致数量均拒绝。
到期子类型保留在输入和计划中，OMS 按已有 EXPIRED 状态处理。

原 OMS 浮点行明确仅作订单读模型；不由这些行生成现金、手续费、资金费或盈亏。
金额仍由原 Decimal 回执账本处理，OMS 恢复不会宣称 `cash_reconciled=true`，也不
代替唯一现金投影的独立比较或后续真实场所验证。
