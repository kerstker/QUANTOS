# Demo 批次风险与提交前持久化

2026-09-12。承接[执行实施顺序](../plans/2026-09-12-demo-execution-completion.md) D0/D2。
本批包含离线准备链、受保护执行进程的内部发送/查询接口及故障验证。
没有实际发送订单、安装签发密钥或部署本批源码。

## 已实现

`live/execution/demo_batch_risk.py` 将原生 BTC 数量、数量上限和成交量按同一固定
百万分之一单位转换后送入现有 `services/risk/pre_trade`。风险门的金额计算仍为
原有浮点实现，精确名义上限另行核对，不声称它已成为 Decimal 现金账本。
同侧所有可独立成交组合、双向总换手、减仓总量、日损失、行情时间、容量、重复、
速率和当前 kill-switch 都被检查。完整输入和风险事件保留，以便复现。

`live/execution/demo_pre_submit.py` 绑定真实起点身份、钱包、空仓范围、行情、
场所网格、已有验证材料和 mandate，再绑定固定注册表、进程启动身份及恢复状态。
速率历史从现有 OMS 读取，不能通过调用方省略旧订单规避。数据库文件上的排他锁
覆盖检查、签名验证、一次性预留及所有恢复/OMS 意图写入，避免两个批次同时
使用同一份空风险状态。批准先持久化，所有 client ID 再写 UNKNOWN/PENDING_NEW；
期间失败不退款、不生成成交，也不重新使用原 ID。

起点采集新增 `DEMO_EXECUTION_ORIGIN_V2`，保留场所返回的普通/条件订单数量上限。
旧 V1 原始文件和严格结构仍可读取；缺少实际过滤器参数的 V1 不能用于准备提交。
场所数量网格以 minQty 为基点，未知过滤器阻断准备，不静默忽略。

随后用实际输入发现 `POSITION_RISK_CONTROL` 的字段仍未保存，已补
`DEMO_EXECUTION_ORIGIN_V3` 保存所有有界过滤器字段；V1/V2 继续严格按旧形状读取。
发送准备要求认识每个过滤器及其全部字段。对位置控制采用明确的窄工程规则：仅接受
完整字段 `positionControlSide=NONE`，主动限制、缺字段及新字段均阻断。该解释依据
本次官方 Demo 实际响应，不宣称已取得未公开的其他控制语义。其余账户风险门不变。

`live/execution/demo_prepared_execution.py` 新增内部固定批次执行协调器。
固定根目录校验注册表/进程 UID、状态文件与证据归属；逐单重新核验当前签名、
撤销、真实当前时间、原起点、风险、mandate 和恢复/OMS 意图。签名上下文保持原冻结身份，
当前风险单独重算。发送前在同一 SQLite 输入日志同步提交唯一发送标记；
读取凭证后、网络前再检查，任何可能发送的原 ID 都不自动重发。

传输位于 `live/exchange/binance_demo_exact.py`，固定 Demo `/fapi/v1/order`，
精确十进制参数和 ACK 请求，默认 TLS 校验，禁重定向/环境代理，无 POST 重试。
从固定受保护文件读取凭证并核对账户命名空间。返回只保留白名单事实和有界原因，
大订单编号保留字符串；不记录私有错误正文。ACK 不转为成交，不写现金或费用。

原 client ID 的有限 GET 查询在批准过期/进程重启后仍可执行，先读当前服务端时钟，
再追加查询结果。`-2013`、请求失败、身份不符、未来或早于本次预留的订单均保持未知。
部分成交只作为累计数量观察保留，不能由两次累计值之差捏造费用或逐笔成交。
