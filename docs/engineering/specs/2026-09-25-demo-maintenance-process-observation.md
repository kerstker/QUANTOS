# Demo维护窗口中的进程元数据检查

承接[启动抑制与窗口接线](2026-09-25-demo-maintenance-start-inhibition.md)。
暂停固定单元并排空其cgroup，不能发现额外执行子进程、旧控制器或人工进程。

## 实现及接线

新增 `tools/demo_maintenance_processes.py`。实际入口要求root，以既有配置确认的
执行/签发UID检查当前进程，不能自动提权或提供任意PID豁免；仅排除协调器自身。
读取有界的/proc/stat、status、cgroup、maps及cwd/exe/fd链接元数据，
不读取命令行、环境变量、映射内存、状态文件正文或凭证，不发送信号或终止进程。

以下观察会报告阻挡记录，仅返回PID、启动tick与固定原因，不输出路径和进程原文：

- 实际/有效/保存/文件系统UID中任意一个属于执行或签发身份；
- 任意quantos-demo-* cgroup，包括不在原42单元名单中的动态子服务；
- 三个受保护状态根中的cwd/exe、打开句柄或文件映射；
- root进程的cwd/exe位于QUANTOS发行版或环境目录。

解析stat时支持comm中空格和括号；比较启动tick防止PID复用混淆，前后核对UID和
fd集合。扫描两轮并比较全部观察，权限失败、进程/句柄变化、超预算或格式不明
均返回PROCESS_SCAN_INCOMPLETE，不能当作空进程集合。核线程及已退出僵尸缺少
用户空间exe/cwd的情况单独处理，专用UID/cgroup仍保留为阻挡理由。

`demo_maintenance_window.check_processes`只在本boot、同目录身份、PAUSED窗口内
运行，持有窗口锁，并在扫描前后重验有效抑制条件、原单元配置及cgroup空闲。
后验暂停丢失时不发布成功摘要；报告保存于该窗口的私有process-check.json。
检测到进程时不擅自终止它，也不自行恢复服务；协调器可保留窗口或显式恢复原状态。

## 验证

新增13项进程测试及2项窗口接线测试，与窗口、抑制、配置及原服务维护联合65项通过。
包括真实子进程打开临时受保护文件后的句柄检测、无fd但有映射、PID身份变化、
目录权限拒绝、已删除目标、相似路径前缀、僵尸和扫描期间暂停丢失。测试不访问
真实账户、生产文件或凭证，未以root在现场运行全进程扫描。Ruff通过。

## 明确保留的限制

这是点状元数据观察，不是内核提供的全局原子快照。人工root程序可能暂时没有
句柄，随后才打开状态；不同挂载命名空间/绑定挂载可能改变路径名称。本次没有
通过路径前缀扫描解决这些问题，manual_exclusion_proven、atomic_snapshot和
quiescence_proven始终false。结果不能落盘后当成后续归档的授权令牌。
后续生产操作仍需要操作员控制的独占窗口、新鲜引用/备份绑定和原有写锁。

核对原生读取代码后，精确origin历史读取仍依赖原文件位置；当前隔离归档的
lookup接口不能直接用于受保护生产根。正式入口必须保留全部受引用原文件，
并明确提供归档查询/回滚路径。不得借本次进程检查移除隔离库的生产根拒绝，
或把“NO_SCOPED_PROCESS_OBSERVED”改写为所有引用与写入已排除。
生产事务入口、实际容量恢复与维护后的数据新鲜度检查仍未完成。
