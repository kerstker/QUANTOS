# QUANTOS 机构式自动 Alpha 与中频交易平台设计

- **日期**：2026-08-06
- **状态**：用户批准
- **首期市场**：Binance USDT 永续合约
- **目标频率**：1–4 小时级中频
- **核心原则**：研究自治，资本受控

## 1. 背景与目标

QUANTOS 当前已经具备较完整的研究、验证、Paper、风险、授权、测试网执行、对账和审计基础，但真实形态仍是以周频任务和只读快照为主的 `L2_DRY_RUN_ONLY` 平台。现有执行链偏向可靠的批处理，不具备小时级持续行情、事件驱动订单管理和实时风险循环；现有前端主要是分散的研究证据页面，还不是专业交易操控台。

目标系统应具备以下能力：

1. 持续接入带逐时点语义的 Binance 永续市场数据。
2. 每天自动生成 1 万–10 万个受约束 Alpha 候选。
3. 自动完成去重、无前视验证、成本容量检验、Shadow/Paper 前向观察、衰退和淘汰。
4. 新 Alpha 首次获得真钱额度时必须由真人审核；批准后，系统可在签署的限额和期限内按 1–4 小时节奏自治调仓。
5. 提供中文为主、对象工作区、最大信息密度的专业综合操控台。
6. 保留并强化现有安全边界：AI 不能批准自己、扩大真钱额度、修改风险限额、接触凭证或绕过 kill-switch。

提高频率不是收益保证。任何策略只有在费用、滑点、资金费、冲击和容量约束后的前向证据成立时，才有资格申请真钱额度。本设计不把 1–4 小时系统称为高频交易（HFT）。

## 2. 已确认的产品决策

| 维度 | 决策 |
|---|---|
| 交易频率 | 1–4 小时更新信号，持仓数小时至数天 |
| 自动化边界 | 真人签署有限、限时授权；授权范围内自治，越限或异常转人工 |
| 首期市场 | Binance USDT 永续合约 |
| 新 Alpha 上线 | 机器可自动推进到 Paper；首次真钱额度必须人审 |
| 候选范式 | 机构式 Alpha Garden，多范式海量候选后统一验证 |
| 候选吞吐 | 每天 1 万–10 万个候选 |
| 交易宇宙 | 按逐时点流动性、历史、价差和数据完整性动态筛选 30–80 个合约 |
| 总体路线 | 研究先行：Alpha→Paper，随后执行，最后完成专业前端替换 |
| 前端结构 | 对象工作区，最大信息密度 |
| 前端语言 | 中文为主，代码符号、交易所字段和标准缩写保留英文 |

## 3. 总体架构

### 3.1 市场数据平面

市场数据平面负责 Binance WebSocket 和 REST 数据接入，覆盖：

- 逐笔成交、最优盘口及必要的订单簿数据；
- 1 分钟和 5 分钟基础 bar，并确定性聚合为 1 小时和 4 小时 bar；
- 资金费、标记价格、持仓量及合约元数据；
- 动态 30–80 币逐时点宇宙；
- WebSocket sequence、缺口检测、REST 补洞和校验；
- 原始数据原子落盘、版本、内容摘要和血缘。

所有观测必须区分：

- `event_time`：市场事件发生时间；
- `knowledge_time`：系统最早可知时间；
- `as_of`：快照或派生值截止时间；
- `freshness`：相对于服务等级目标的新鲜度；
- `sequence` / `watermark`：增量完整性与可补洞水位。

出现断流、序列缺口、时间倒退、校验失败或关键字段陈旧时，数据门必须阻止新交易意图；不得以旧快照或合成数据假装正常。

### 3.2 Alpha Garden

Alpha Garden 每天生成 1 万–10 万个候选，覆盖：

- 截面多空因子；
- 单资产时间序列信号；
- 资金费、OI、基差和期限结构；
- 价格、成交量、波动率和市场状态；
- 因子组合与交互；
- 固定、受约束的机器学习模型模板；
- 现有 GP、MCTS、进化搜索和 bandit 算力分配能力。

AI 生成的是类型安全的表达式、参数和已登记模型模板，不是任意可执行 Python。允许的字段、窗口、操作符、训练方法、随机种子、资源预算和输出形状由版本化注册表限定。

每个候选都有稳定身份：

```text
alpha_id = hash(
  canonical_definition,
  feature_contract,
  data_version,
  universe_rule,
  horizon,
  cost_model,
  validation_policy
)
```

同一想法的不同参数不能被当成大量独立发现。系统按表达式血缘、输入重合、收益相关性和行为特征聚类，以家族为单位计数和控制多重检验。

### 3.3 证据工厂

证据工厂把候选依次送入固定验证漏斗：

1. **生成**：每天 1 万–10 万候选。
2. **低成本初筛**：AST/类型安全、canonical 去重、数据覆盖、有限值、换手合理性、初步 IC 和相关性。
3. **样本外验证**：purged walk-forward、embargo、no-peek、Deflated Sharpe、PBO、BH-FDR、市场状态稳定性和尾部风险。
4. **交易现实检验**：bid/ask、手续费、资金费现金流、换手、冲击、容量、参与率、动态宇宙和组合增量价值。
5. **Shadow/Paper**：严格 post-cutoff、先记录信号后兑现结果、覆盖率门、现实差距、TCA、漂移和衰退。

候选吞吐不能通过跳过昂贵门禁来维持。系统必须允许当天 0 个通过者。

### 3.4 Trial Ledger

Trial Ledger 是全局不可变试验账本。每次成功、失败、重复、取消和中断都必须记账，至少绑定：

- `trial_id`、`alpha_id`、家族和父代；
- 输入数据、代码、配置和环境摘要；
- 随机种子和算力预算；
- 验证政策和有效试验数；
- 输出 artifact 摘要；
- 状态、失败原因和时间水位。

后续结果不得覆盖早期结果。验证门槛不得因结果不理想而事后调整；若政策改变，必须形成新版本和新试验。

### 3.5 生命周期

目标生命周期为：

```text
DISCOVERED → TESTING → VALIDATED → SHADOW → PAPER → REVIEW_REQUIRED
```

机器可以：

- 自动推进至 `PAPER`；
- 自动暂停、降级、去风险和退休；
- 在新证据不足时保持原状态或拒绝；
- 将通过全部机器门禁的候选送入真人审查队列。

机器不能：

- 自行获得首次真钱额度；
- 将 `APPROVED` 解释为真钱授权；
- 修改 mandate 的资金、风险、交易所、账户或期限；
- 自动复位 kill-switch；
- 因收益下降而扩大资金、杠杆或范围。

### 3.6 组合意图层

组合意图层接收已通过相应生命周期门的 Alpha sleeve，负责：

- 风险预算和相关性去重；
- 账户级 gross、net、集中度、拥挤度和容量约束；
- 每 1–4 小时生成目标仓位；
- 计算目标与当前仓位的差值；
- 生成调仓预览和签名决策回执。

该层不持有交易所凭证，不直接调用 exchange adapter，也不具备 broker capability。

### 3.7 人类授权与执行控制面

新 Alpha 首次申请真钱额度时，必须经过外部强身份和多方真人审核。授权绑定：

- `alpha_id` / 策略版本；
- 账户和 Binance USDT 永续；
- 生效期与到期时间；
- 最大资金、gross/net、单币集中度、回撤、保证金、参与率和订单限制；
- 允许的订单类型和执行策略；
- 审批主体、证据摘要和一次性 grant。

执行控制面必须是独立进程和权限域，只接受验证通过、签名且未消费的输入。它负责：

- pre-trade gate 与 mandate；
- OMS 订单事件状态机；
- Binance 下单、查询、撤单和恢复；
- 成交、TCA、持仓、权益和账户级对账；
- 实时风险、kill-switch 和独立 reduce-only 应急路径；
- append-only 审计和执行回执。

授权范围内可以自治；授权到期、身份失效、数据异常、风险越限、模型衰退或对账偏差时，系统停止扩大风险并转人工。AI 无权恢复或扩大授权。

## 4. 运行模型

### 4.1 持续服务，而非高频定时脚本

小时级目标不能通过把现有周度脚本改成每小时运行来实现。目标运行时至少包含：

- Ingest Service；
- Feature Materialization Service；
- Durable Workflow Engine；
- Candidate/Validation Workers；
- Lifecycle and Paper Service；
- Read-model Projectors；
- Governance Service；
- 独立 Execution Service。

首期允许单机多进程，但研究、数据、治理和执行必须分进程、分权限。执行进程独占凭证；研究和前端永远看不到凭证。

### 4.2 事件与命令日志

状态变化通过 append-only event log 和 command journal 记录。命令必须包含：

- `command_id` 和幂等键；
- actor 的不可变身份；
- 目标对象及预期版本；
- 业务理由和授权引用；
- 输入水位和 schema 版本；
- 结果、错误和审计摘要。

工作流使用持久租约、single-flight、checkpoint 和重试预算。worker 崩溃后从 checkpoint 恢复，同一 `trial_id` 或 `client_order_id` 不得产生重复副作用。

### 4.3 实时前端协议

专业前端先获取带 watermark 的完整快照，再接收增量：

- SSE：生命周期、验证、工作流、风险、治理和审计等控制事件；
- WebSocket：行情、订单和成交等高更新频道；
- REST：完整快照、历史查询和幂等命令提交。

断线重连携带 cursor 补洞；补洞失败则重新获取快照。所有响应统一包含 `schema_version`、`as_of`、`freshness`、`watermark` 和逐字段 provenance。

真实模式中，后端错误、字段缺失、未知 schema 或数据陈旧必须显式显示，禁止隐式回退 mock。演示模式和真实模式永久视觉区分。

## 5. 故障处理

| 故障 | 自动响应 | 恢复条件 |
|---|---|---|
| WebSocket 断流或序列缺口 | 数据标记不可用，REST 补洞，禁止生成新交易意图 | 序列连续、校验一致、新鲜度恢复 |
| 候选或验证 worker 崩溃 | 租约到期后从 checkpoint 重跑，同一 trial 幂等 | 输出摘要与输入绑定一致 |
| 证据缺失、版本漂移或哈希不一致 | 候选 `BLOCK`，不得回退旧证据 | canonical 证据重新生成并校验通过 |
| 订单 ACK 后状态不确定 | 按 `client_order_id` 权威回查，禁止盲目重发；必要时撤单再回查 | 交易所终态与本地账本一致 |
| 仓位、权益或成交对账偏差 | 停止加仓，闩锁 kill-switch；只允许独立 reduce-only 安全路径 | 人工核验并按多方流程复位 |
| 模型衰退或成本恶化 | 自动降风险、暂停或退休 | 新证据通过；真钱恢复重新人审 |
| mandate 到期或身份失效 | 停止新增风险并转人工 | 新授权生效 |

## 6. 专业综合操控台

### 6.1 设计原则

操控台不复制 Bloomberg 的视觉外观，而采用专业终端原则：

- 高信息密度；
- 对象上下文；
- 键盘优先；
- 全局状态常驻；
- 异常优先于装饰；
- 所有关键数字可追溯；
- 读写权限清晰分离。

默认中文，代码标识、交易所字段和通用缩写保留英文。默认最大信息密度，支持保存布局、多显示器、表格虚拟滚动、全局搜索和命令面板。

### 6.2 全局状态条

全局状态条始终显示：

- 环境：L2 / Paper / Testnet / Micro-Live；
- venue 与账户；
- 市场数据新鲜度；
- 当前 event watermark；
- kill-switch；
- mandate 状态和到期时间；
- 关键告警；
- 当前操作者和身份强度。

### 6.3 五个对象工作区

1. **首页 / Market Monitor**：市场状态、全局收益风险、数据新鲜度、告警、事件带和下一次调仓。
2. **Alpha Control Plane**：候选 blotter、血缘、家族、IC/OOS、生命周期、自动任务和证据 drill-down。
3. **Validation Evidence**：Trial Ledger、回测、成本容量、反证矩阵和 Shadow/Paper 现实差距。
4. **Portfolio & Risk**：sleeve、目标仓位、风险预算、敞口、归因、漂移、衰退和应急状态。
5. **Execution & Orders**：Paper/Testnet/Live 环境、订单事件、成交、TCA、对账、mandate 和待审队列。

研究运行、审批治理、审计事件和系统健康作为全局抽屉，不再各占顶级页面。现有 Getting Started、重复研究结论页、陈旧重定向和合成蓝图页删除或归档为文档。

### 6.4 安全操作模型

前端不直接调用交易所 adapter。写操作通过治理或执行控制面，必须具备：

- 强身份和 RBAC；
- 幂等键；
- 目标对象版本；
- 业务理由；
- 预期影响预览；
- 一次性回执和审计。

高影响操作采用：

```text
预览 → 风险差异 → 多方批准 → 一次性执行 → 权威回查 → 审计回执
```

不得使用浏览器 `prompt` 或自报 reviewer 作为授权依据。

### 6.5 图表和状态表达

- 颜色只承担固定系列、幅度、正负或状态之一，不混用；
- 状态颜色必须同时使用图标和文字；
- 多系列图始终有图例，且实体颜色稳定；
- 禁止双 Y 轴；不同量纲使用小多图或指数化比较；
- 可交互图默认有 hover、tooltip 和表格视图；
- 深色模式独立验证，不做简单反色；
- 关键字段展示来源、as-of 和 freshness。

## 7. 分阶段交付

### Wave 0：可信基线

目标：修复当前验证失败和证据漂移，确保后续开发建立在同一可信基线上。

范围：

- 修复当前 5 个测试失败；
- 适配 FastAPI 0.139 路由契约；
- 修复治理扫描器字面量问题；
- 处理依赖版本漂移和前端 eslint；
- canonical 重生成 readiness、供应链、top-tier 和验证证据；
- 保留并隔离当前工作树中已有证据与报告改动。

验收：

- `python scripts/validate.py` 全绿；
- 所有 readiness 绑定当前 commit 和同一验证运行；
- 无互相矛盾的 generated-at/commit/current 状态；
- 系统仍保持 `L2_DRY_RUN_ONLY`。

### Wave 1：小时级 Alpha Garden 到 Paper

范围：

- 小时级 PIT 数据与动态宇宙；
- 类型安全候选注册表和生成器；
- 每天 1 万–10 万候选吞吐；
- 全局 Trial Ledger、家族聚类和有效试验计数；
- 分层验证 DAG 和算力预算调度；
- Shadow/Paper、现实差距、漂移、衰退和退休；
- Alpha→Paper 的只读高密度工作区。

验收：

- 连续运行至少 7 天；
- 同输入、版本和种子产生相同候选、证据和排名；
- worker 崩溃、重复任务和调度重启可恢复；
- 每个 Paper Alpha 可追溯完整数据、trial 和证据链；
- 系统可以产生 0 个通过者；
- 不新增真钱能力。

### Wave 2：1–4 小时限额内自治执行

范围：

- Binance 行情流与 gap recovery；
- 常驻 scheduler 和 OMS 订单事件状态机；
- 实时风险、账户级对账、TCA 和故障恢复；
- 独立执行权限域和签名输入；
- 先 Paper/Testnet soak，再准备 Micro-Live 人工门。

进入 Micro-Live 前必须具备：

- 外部 IdP、可信 TLS/mTLS 和密钥生命周期；
- 独立签名权威和进程隔离；
- 人工签署 mandate；
- 足够的前向、Paper/Testnet 对账和故障演练证据；
- 独立 Go/No-Go 审核。

验收：

- 行情断流、乱序、重复、部分成交、撤单竞态、API 超时、账本写失败和进程崩溃演练通过；
- Paper 与 Testnet 连续对账；
- 未获有效 grant 时结构性零提交；
- grant 到期或异常时自动停止新增风险。

### Wave 3：专业操控台全面替换

范围：

- 统一 snapshot/delta schema；
- 五个对象工作区；
- 治理、审计、健康和任务全局抽屉；
- 真实命令模型和多方批准体验；
- 删除重复、陈旧、合成和不可达前端面。

验收：

- 真实模式无隐式 mock；
- 断线可补洞，补洞失败显式重载；
- 每个关键字段可见来源、时点和 freshness；
- 所有命令具备身份、RBAC、幂等和审计；
- 页面用途与数据源 manifest 唯一，聚合页不重复完整子页面；
- 浏览器端到端验证关键读写流程。

## 8. 测试策略

### 8.1 确定性核心

- DSL、特征、PIT、统计、组合和风险纯函数单元测试；
- 性质测试覆盖无前视、资金守恒、仓位不扩大、幂等和稳定身份；
- 固定模型模板要求同输入 bit-identical 或在明确容差内确定性。

### 8.2 契约与集成

- schema 兼容、时间单位、watermark 和 cursor；
- 数据库迁移、并发写、append-only 和崩溃恢复；
- 交易所 fake 必须模拟异步、部分成交、丢响应、重复、乱序和陈旧等最不方便行为；
- 测试 snapshot + delta 重建出的 read model 与权威状态一致。

### 8.3 故障与回放

- WebSocket 缺口、REST 补洞失败和时间倒退；
- worker kill、租约到期、重复命令和 checkpoint 恢复；
- 订单 ACK 不确定、撤单成交竞态和账本写失败；
- kill-switch 跨进程闩锁、reduce-only 应急通道和三方复位；
- 事件日志从零重放后得到相同状态。

### 8.4 端到端观察

- 驱动真实应用完成 Alpha→Paper；
- 测试网订单全生命周期；
- 浏览器观察工作台实时状态、断线重连、命令预览、审批和回执；
- 非平凡产品代码变更必须进行实际运行验证，而不只依赖单元测试。

## 9. 非目标

首期明确不做：

- 毫秒/秒级 HFT、共址和低延迟二进制撮合协议；
- 同时扩展 Bybit、MEXC、现货和跨所套利；
- AI 自主批准真钱、扩大资本或修改风险数字；
- 任意代码生成并直接进入研究或执行进程；
- 通过提高频率或放松门禁承诺收益；
- 为追求页面效果先建设没有真实数据契约的漂亮空壳。

接口保持 venue 可插拔。Binance 永续闭环稳定后，再以独立设计扩展其他交易所和策略频率。

## 10. 最终完成定义

目标系统能够：

1. 持续接入并验证小时级 Binance 永续数据；
2. 每天生成并诚实淘汰 1 万–10 万个候选；
3. 自动把极少数 Alpha 推进至 Shadow/Paper，并自动暂停、降级或退休失效候选；
4. 让真人在专业前端审查完整证据并授予有限、限时的首次真钱额度；
5. 在有效授权内按 1–4 小时节奏自治调仓；
6. 在任何数据、证据、身份、风险、授权或对账异常下停止扩大风险；
7. 对每个研究判断、批准、订单、成交和状态变化提供可重放、可审计证据。

这一定义衡量的是系统闭环、可复现性和安全自治能力，而不是承诺一定数量的上线 Alpha 或一定收益。
