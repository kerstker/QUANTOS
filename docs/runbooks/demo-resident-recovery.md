## 输入与运行

入口为 `python -P -m tools.demo_resident_recovery --source-commit <完整40位源码> --serve`。
省略 `--serve` 只运行一次。源码参数是来源记录；它本身不认证部署或授予交易权限。
实际运行必须使用验收后的不可变安装源码和对应 Python 3.12 环境。

部署先具备以下已有边界，工作者不会自动创建或补造它们：

| 固定路径 | 内容与控制 |
|---|---|
| `/etc/quantos/demo-submission/authority.json` | 独立安装的 Demo 注册表；全部路径组件由 root 控制，当前进程 UID 必须等于注册表 executor_uid |
| `/etc/quantos/demo-submission/credentials.json` | 已有专用 Demo 凭证格式；仅固定查询边界读取并核对账户摘要；不会从研究 key 目录自动复制 |
| `/var/lib/quantos-demo-executor/dispatch.sqlite3` | 原批准预留和发送/查询日志 |
| 同目录 `recovery.sqlite3`、`oms.sqlite3`、`order-events.sqlite3` | 原恢复状态、原订单读模型及原订单事件日志 |
| 同目录 `user-stream.sqlite3` | 执行侧自己采集的私有输入；研究可写副本不能代替 |
| 同目录 `evidence/` | 原始提案及已有查询/撤单证据 |
| 同目录 `resident-recovery/` | 本工作者追加尝试、报告及显示副本；不保存另一份现金账 |

执行目录和文件属于专用 executor UID，禁止组/其他用户写；文件为普通单链接文件。
注册表和凭证仍属于 root。需要给专用 executor 适当的只读组权限，不能因此赋予研究进程访问。
缺失目录、文件、注册表、错误 UID、符号链接或损坏日志均在实际查询前拒绝。
工作者不导入旧 JSON kill-switch，不初始化或复位任何交易闸；查询恢复本身不会增加风险。

## 恢复流程

1. 读取原预留、原 OMS 和原恢复记录，在最多 1,000 份/合计 64MiB 的原始提案中查找唯一内容匹配。
   即使准备函数崩溃、调用者丢失返回值，也从原事实重建查询句柄；不会产生新的批准或发送意图。
2. 保存本次查询尝试后，调用原受保护 `query_reserved`，仅查原 client order ID。
   新进程不沿旧批准重新发送。缺提案、歧义或坏摘要保留待查编号；没有发送标记的记录也不会被自动认作不存在。
3. 查询起始时间至少相隔 30 秒；节奏记录在重启后继续有效。10,000 次尝试后停止追加并显示预算耗尽，
   不删除旧记录继续计数。不清楚的订单保持未知，查询结果并不等于私有回执或现金结果。
4. 有受保护私有输入时，按首次发送标记至本轮查询前的既有范围配对。范围仍受 150 秒、
   原时钟探针和同 UTC 容量日限制；越界显示未解决，不延长旧合同或选取有利子窗口。
   包含2026-09-14历史恢复增量的工具，会优先使用原已留存终态查询所固定的历史窗口，
   并另行核对最新查询是否冲突；原缺口和窗口限制不变。此前一次实际恢复绑定3,991毫秒，
   仍因STREAM_GAPS_IN_WINDOW拒绝入账，不能将选定历史窗口视为缺口消失。
5. 原回执/原查询一致后，调用既有唯一回执回放及原 OMS 幂等投影，再收敛恢复记录。
   原始费用仍由唯一 V2 处理，工作者不额外记费或自动宣称现金相符。

一次循环受专用进程锁保护；等待时每秒检查停止信号。网络调用仍用原有固定 Demo 地址、
无重定向/代理继承/自动下单重试的有界传输。服务停止等待最长 75 秒，超时由 systemd 结束整个进程组；
已保存的查询尝试保留，下次启动沿原编号恢复。

## 可审阅的服务与只读界面

`scripts/render_demo_recovery_unit.py` 接受完整源码、专用执行 UID 和新输出目录，
生成绑定 `/opt/quantos/releases/<commit>` 与 `/opt/quantos/venvs/<commit>` 的服务文件和摘要。
文件没有 `[Install]`，渲染不安装、不启用、不启动服务，不更改注册表或密钥。
这不是现有研究/L2 模板的替换；研究服务仍不能读取该执行侧状态或凭证。

实际安装前还须核实独立注册表、专用 UID、目录权限、实际采集者、原预留输入、源码验收和运行时依赖。
渲染器的摘要不代替这些事实，不把测试夹具签名安装成实际信任根。

工作者在 `resident-recovery/views` 保存当前心跳，在 `resident-recovery/outcomes` 保存上次实际查询结果。
两者使用不可变显示记录，各自保留来源时间。现有工具 `tools.demo_oms_status_publish --kind resident`
可以分别发布两类已验证显示记录到独立研究缓存：

- `data/cache/binance_demo_resident_status/views`
- `data/cache/binance_demo_resident_status/outcomes`

发布者需要源只读权限和目的地写权限；研究 Console 只读取目的地副本，不用于执行恢复。
不同身份之间的最终只读权限/发布服务尚未安装，不能将“工具可以复制”写成实际常驻发布完成。
Studio 在原“订单恢复进度”内显示心跳、尝试节奏、上次失败和未解决项；超过 120 秒的心跳明确过期。
刷新只读取当前快照。工作者停止、输入损坏与尚无记录均不显示成功或零失败。
执行侧原始记录可由[只读观测入口](../engineering/specs/2026-09-13-demo-executor-observation.md)
汇总到研究界面；研究 Console 只读取独立展示副本，不能读取受保护数据库或反向写入。
该发布链仍需实际执行身份及复制权限安装，不能用研究采集记录冒充已经完成部署。
